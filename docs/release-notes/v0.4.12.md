本版本修掉两处宠物相关的缺陷：市场安装被中断留下的暂存目录不再顶替同名宠物，设置页在插件开关打开后也能立刻读到宠物列表，不必刷新页面。版本号跟上家族统一的 0.4.12。

> **兼容性**：没有破坏性变更，也无需手工迁移。包名 `@linxin666/dsh-pet` 与安装方式不变；`dsh.engines.dsh` 的声明与下限本轮不动，仍是 `>=0.2.1-rc.3`，peer 依赖下限同样不动。持久化标识不变：布局与游戏进度仍写在 `$DSH_HOME/pet.json`，键名一个不改；宠物资产仍落在 `$DSH_HOME/pets/<id>/`；语音包分层与状态装饰目录不变。线协议字段与设置字段名（`petId`、`statusBubbles` 等）都不变，旧配置文件直接可用。注册表的扫描语义只多一条：形如 `<id>.install-<...>` 的暂存目录被跳过并给出警告，其余目录的优先级与覆盖关系原样保留。

### 修复

- 中断的市场安装不再顶替同名宠物（dsh-web issue 1952 的 dsh-pet 一半）：市场安装器先把内容下载进同级暂存目录 `<id>.install-<base36 毫秒>-<base36 随机>`，成功才改名到 `<id>`，失败则删除；宿主在这两步之间被杀就会留下它。`src/registry.ts` 的 `scanPetDir` 此前把它当成普通宠物目录去读，而 `readdirSync` 的名字有序让 `<id>` 排在 `<id>.install-...` 之前、`loadPetRegistry` 又让后出现的条目赢下同 id 冲突，于是半成品覆盖掉装好的那只宠物，图集或帧轨道不全且没有任何说明
- 识别用的是产出方的真实形状而不是前缀匹配：`PET_INSTALL_STAGING_NAME` 为 `/\.install-[0-9a-z]{1,11}-[0-9a-z]{1,11}$/`（`Date.now()` 的 base36 今天 8 位、数千年内不超过 11 位，`Math.random().toString(36).slice(2, 8)` 恒为 6 位），仅仅名字里含 `.install-` 的其他形状仍按普通宠物目录处理
- 跳过发生在读 `pet.json` 之前，并且只报告不修复：一条警告字符串加一条 `level: 'warning'` 的 `PetRegistryDiagnostic`，`source` 指向残留目录，用户可据此自行删除；扫描保持只读，不删除、不改名、不挪动任何东西。这条报告不依赖残留目录里有没有 manifest，死在第一个文件的失败安装同样会被说明
- 设置页开关打开后宠物列表立即填充（#25，Nwflower 贡献）：注册表只在插件启动时读一次，而宿主只在插件启用期间注册 `/api/pet/*`，所以打开总开关后选择器一直为空，必须刷新页面；那时延后的读取已经用完三次重试。卡片现在一渲染出「插件已启用且没有任何可选宠物」就重新读一次注册表，并用在途标记把这次读取与构造函数的首次读取合并成同一个请求。列表请求带 `cache: 'no-store'`，禁用状态下被缓存的 404 不能再代答

### 其他改动

- 决策记录：新增 `2026-10-27-pet-registry-skips-install-staging-leftovers`（暂存目录的形状、只报告不删除，以及被否掉的替代方案）与 `2026-10-28-pet-intake-round`（三个 fork PR 的评审与合并结论）
- 测试：`src/registry.test.ts` 补齐暂存目录名的识别、读 `pet.json` 之前跳过、报告内容与「仅仅含 `.install-` 的名字不算暂存」的用例；`src/client/PetSettingsCard.test.tsx` 新增开关打开后重新读取的回归用例，`tests/pet-section.spec.tsx` 随卡片接口调整
- 版本：`package.json` 的 `version` 从 0.4.11 抬到 0.4.12，与 dsh-web 家族统一版本号对齐（卫星先发、主仓后发）
- `lib/` 不入库（在 `.gitignore` 里），由 `prepare` 脚本在发布时现场重建，因此本次没有随之改动的已提交产物；本说明文件不在 npm 包的 `files` 白名单里，不会进入发布产物

This release fixes two pet defects: a staging directory left behind by an interrupted market install no longer overrides the pet of the same id, and the settings page reads the pet list the moment the plugin switch opens instead of waiting for a page reload. The version number follows the unified family version 0.4.12.

> **Compatibility**: nothing breaks and no manual migration is needed. The package name `@linxin666/dsh-pet` and the install path are unchanged; the `dsh.engines.dsh` declaration and its floor stay untouched this cycle at `>=0.2.1-rc.3`, and so do the peer-dependency floors. Every persistence identifier keeps its name: layout and gameplay progress still live in `$DSH_HOME/pet.json` with identical keys, pet assets still land in `$DSH_HOME/pets/<id>/`, and the voice-pack layering and the status-decoration directory are unchanged. Wire-protocol fields and the settings field names (`petId`, `statusBubbles` and the rest) are unchanged, so an existing configuration file keeps working as written. The registry scan gains exactly one rule: a directory shaped like `<id>.install-<...>` is skipped with a warning, and every other directory keeps its previous precedence and override semantics.

### Bug Fixes

- An interrupted market install no longer overrides the pet of the same id (the dsh-pet half of dsh-web issue 1952): the market installer downloads into a sibling staging directory named `<id>.install-<base36 ms>-<base36 random>`, renames it onto `<id>` on success and removes it on the failure path, so a host killed between those two steps leaves it behind. `scanPetDir` in `src/registry.ts` used to read it as an ordinary pet directory, and two facts then combined: `readdirSync` names are sorted so `<id>` comes before `<id>.install-...`, and `loadPetRegistry` lets the later entry win the id collision. The partial download therefore replaced the working pet, with an incomplete atlas or frame tracks and no explanation
- Recognition follows the producer's real shape rather than a prefix test: `PET_INSTALL_STAGING_NAME` is `/\.install-[0-9a-z]{1,11}-[0-9a-z]{1,11}$/` (base36 of `Date.now()` is 8 digits today and stays under 11 for several millennia, and `Math.random().toString(36).slice(2, 8)` is always exactly 6 characters), so a name that merely mentions `.install-` outside that shape stays an ordinary pet directory
- The skip happens before `pet.json` is read and is reported, not repaired: one warning string plus one `PetRegistryDiagnostic` with `level: 'warning'` and `source` set to the residual directory, so a user can delete it themselves; the scan stays read-only and never deletes, renames or moves anything aside. Reporting does not depend on the leftover holding a manifest, because a failed install that died on its first file is exactly the case a user needs told about
- The pet list fills in as soon as the settings switch opens (#25, contributed by Nwflower): the registry was read once at plugin start, and the host registers `/api/pet/*` only while the plugin is enabled, so opening the master switch left the picker empty until the page was reloaded; by then the deferred reads had already spent their three retries. The card now re-reads the registry as soon as it renders with the plugin on and no choices, and an in-flight flag collapses that read with the constructor's first load into a single request. The list request carries `cache: 'no-store'`, so a cached 404 from the disabled state can no longer answer for it

### Other Changes

- Decision records: `2026-10-27-pet-registry-skips-install-staging-leftovers` (the staging shape, reporting instead of deleting, and the rejected alternatives) and `2026-10-28-pet-intake-round` (the review and merge verdicts for three fork PRs)
- Tests: `src/registry.test.ts` covers staging-name recognition, the skip before `pet.json` is read, the warning content, and a name that merely mentions `.install-` staying an ordinary pet directory; `src/client/PetSettingsCard.test.tsx` adds the regression case for the re-read after the switch opens, and `tests/pet-section.spec.tsx` follows the card's interface change
- Version: `version` in `package.json` moves from 0.4.11 to 0.4.12 to follow the unified dsh-web family version (satellites ship first, the main repository follows)
- `lib/` is not tracked (it sits in `.gitignore`) and is rebuilt on the spot by the `prepare` script at publish time, so no committed artifact moves with this release; this notes file is outside the npm package's `files` whitelist and never reaches the published artifact
